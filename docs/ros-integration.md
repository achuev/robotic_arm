# Интеграция с ROS 2: что проверено на живой системе

Результаты спайка (этап 0). Всё ниже — не из документации, а снято с работающего
контейнера `so101-ros:dev` в режиме `hardware_type:=mock`.

## Запуск

```bash
docker build -f deploy/Dockerfile.ros --build-arg WITH_IK=1 -t so101-ros:dev upstream
docker run -d --name so101-mock \
  -e ROS_DOMAIN_ID=0 -e RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
  -e ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST \
  so101-ros:dev ros2 launch so101_bringup follower.launch.py hardware_type:=mock use_rviz:=false
```

Контроллеры поднимаются примерно за 2 с. Оба активны:

```
forward_controller       forward_command_controller/ForwardCommandController  active
joint_state_broadcaster  joint_state_broadcaster/JointStateBroadcaster        active
```

Менеджер контроллеров живёт в пространстве имён: `ros2 control list_controllers`
без `-c /follower/controller_manager` не найдёт его и будет молча ждать таймаута.

## ⚠️ Порядок суставов НЕ совпадает между командой и обратной связью

Это главная находка спайка, и она молча ломает робота, если сопоставлять по индексу.

| | Порядок |
|---|---|
| **Команда** `/follower/forward_controller/commands` | `shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper` (из `follower_controllers.yaml`) |
| **Обратная связь** `/follower/joint_states` | `elbow_flex, gripper, shoulder_lift, shoulder_pan, wrist_flex, wrist_roll` (по алфавиту) |

Проверено экспериментом: публикация `[0.5, -0.3, 0.4, 0.0, 0.0, 0.8]` дала
`elbow_flex = 0.4` (третий элемент команды) и `gripper = 0.8` (шестой). Совпадений
между позициями в двух массивах нет ни для одного сустава, кроме симметричных нулей.

**Следствие для `backends/ros2.py`: читать `joint_states` строго по полю `name`,
никогда по индексу.** Индексы совпадут только случайно и только на нулях — то есть
ошибка не проявится ни в одном простом тесте, а на стенде плечо поедет вместо локтя.

## Пределы суставов

Сняты из URDF, сгенерированного из xacro внутри контейнера
(`deploy/so101_follower.generated.urdf`), радианы:

| Сустав | lower | upper |
|---|---|---|
| shoulder_pan | −1.9199 | +1.9199 |
| shoulder_lift | −1.7453 | +1.7453 |
| elbow_flex | −1.6900 | +1.6900 |
| wrist_flex | −1.6581 | +1.6581 |
| wrist_roll | −2.7439 | +2.8412 |
| gripper | −0.1745 | +1.7453 |

`wrist_roll` несимметричен — не «примерно ±2.8», а именно такие границы.
Захват наружу отдаётся нормированным в 0..1 (см. `docs/api.md`), пересчёт внутри шлюза.

## IK-нода и единственная точка публикации команд

```bash
ros2 run so101_kinematics cartesian_motion_node --ros-args -p cmd_topic:=/web/ik_cmd
```

Поднимается **без браузера и без Viser** примерно за 8 с. Даёт сервисы `/go_to_pose`
и `/go_to_joints` (типы из `so101_kinematics_msgs`) и подписку `/servo_target`.

Подмена `cmd_topic` работает, и это проверено на счётчиках издателей:

```
/follower/forward_controller/commands   Publisher count: 0   Subscription count: 1
/web/ik_cmd                             Publisher count: 1   Subscription count: 0
```

То есть IK-нода не пишет в топик команд напрямую; место издателя свободно и
принадлежит шлюзу, который обязан прогнать решение IK через клэмп и ограничитель
скорости, прежде чем публиковать.

## Сборка образа: найденные ловушки

1. **`robokin` отсутствует в PyPI.** Это пакет автора апстрима, ставится только из
   git: `robokin[placo] @ git+https://github.com/legalaspro/robokin.git`.
   Собирается и импортируется нормально. Риск, заложенный в план, закрыт — запасной
   IK не понадобился.
2. **Конфликт numpy.** `robokin` тянет numpy 2.x и scipy 1.18, которые ломают
   `transforms3d` в ROS (`np.maximum_sctype` удалён в numpy 2). Лечение: после
   установки снести pip-версии numpy/scipy и остаться на apt-овых numpy 1.26 /
   scipy 1.11 — с ними работают и placo, и pin, и robokin.
3. **`psutil` под управлением Debian**, pip не может его снести — нужен
   `--ignore-installed psutil`.
4. **Кэш `robot_descriptions` греется на этапе сборки** и его нельзя чистить:
   при отсутствии `.git` или любого отслеживаемого файла библиотека клонирует
   репозиторий заново, уже в рантайме.
5. `colcon build --packages-up-to so101_bringup so101_kinematics` — собирать весь
   воркспейс не нужно и вредно: тракт imitation learning тянет лишние зависимости.
6. `network_mode: host` не работает на Docker Desktop под macOS — в `compose.dev.yml`
   используется проброс портов, а вариант для Linux-стенда оставлен закомментированным.

## ⚠️ Контейнерам мало общей сети — нужна общая разделяемая память

Вторая ловушка, которая стоила времени. FastDDS на одной машине по умолчанию
возит данные через разделяемую память. Если контейнеры делят только сетевое
пространство (`network_mode: service:ros`), получается коварная картина:

- подписчики на топике **числятся** (`Subscription count: 3`),
- данные при этом **не идут вообще**,
- `ros2 node list` чужих нод **не показывает**,
- `/api/health` честно отдаёт 503, и выглядит это как ошибка в коде шлюза.

Лечение: донор объявляется `ipc: shareable`, остальные входят через
`ipc: "service:ros"`. Донор без `shareable` присоединиться не даст:
`can't join IPC of container ... non-shareable IPC`.

Всё это закреплено в `deploy/compose.dev.yml`, стек поднимается одной командой:

```bash
docker compose -f deploy/compose.dev.yml up -d
```

## Положение схвата берётся только из TF

Кадры TF идут **без префикса**: `base_link` → `gripper_frame_link`
(`frame_prefix` в bringup по умолчанию пуст). `follower/base_link` не существует,
`tf2_echo` на него отвечает `Invalid frame ID`.

Считать положение схвата собственной моделью нельзя. Проверено дорого: пока
шлюз брал точку из приблизительной модели `SimBackend`, а IK решал robokin по
настоящему URDF, две геометрии в одном контуре обратной связи **уводили руку —
схват ехал вниз вместо вверх**. После перехода на TF джоггинг по `z` даёт
ровно то, что просили, и упирается в потолок рабочей зоны с честным
`out_of_range`.

Расхождение моделей в одной и той же нулевой позе:

| | x | y | z |
|---|---|---|---|
| Настоящая (TF из URDF) | +0.391 | 0.000 | +0.226 |
| Приблизительная (`SimBackend`) | +0.039 | 0.000 | +0.377 |

В нулях настоящая рука вытянута вперёд, а модель симулятора смотрит вверх.
Из ROS-бэкенда приблизительная модель убрана полностью: до первого TF он держит
`connected = false` и отдаёт нули, а не выдуманную точку.

## Рабочая зона: замер, а не догадка

Обмерено по 144 позам (перебор сетки углов с чтением TF):

| ось | реальный вылет | коробка для демо |
|---|---|---|
| x | −0.329 … +0.469 | 0.15 … 0.38 |
| y | −0.404 … +0.404 | −0.20 … 0.20 |
| z | −0.204 … +0.493 | 0.08 … 0.36 |

Максимальный горизонтальный вылет — 0.469 м.

Границы подобраны замером доли решаемых точек, а не на глаз, и первая догадка
оказалась неверной. Предполагалось, что мешает «дыра» у основания, куда рука не
складывается из-за пределов локтя и кисти, — но поднятие нижней границы x с 0.10
до 0.15 не дало ничего (77.8 % против 77.4 %). Мешают углы коробки по y: прямо-
угольник не вписывается в сферу досягаемости, и широкая зона набирает слишком
много недостижимых углов.

| коробка | решаемо | объём |
|---|---|---|
| x .10–.42, y ±.30, z .05–.45 | 77.8 % | 76.8 л |
| x .15–.40, y ±.25, z .07–.42 | 89.2 % | 43.8 л |
| **x .15–.38, y ±.20, z .08–.36** | **98.9 %** | **25.8 л** |

Взята последняя: 38 × 40 × 28 см для демо более чем достаточно, зато прохожий
почти никогда не упрётся в необъяснимое «рука не дотянется». Из 2197 точек сетки
недостижимы 20, и все — в дальнем верхнем углу.

Домашняя поза (0.293, 0.000, 0.206) внутри с запасом. Нулевая поза (x = 0.391)
намеренно ОСТАВЛЕНА снаружи: там рука вытянута почти в струну при вылете 0.469,
якобиан вырожден, и расширять зону до этой окрестности значит ловить дёрганье.

Умолчания из первоначального плана (x 0.05…0.35) не содержали даже домашней
позы — джоггинг упирался бы в границу с первого нажатия.

## Побочно подтверждено: двух издателей быть не должно

При обмере зоны пробник публиковал команды напрямую в топик руки, а шлюз в это
же время держал свою позицию на 50 Гц. Итог — все 144 позы дали одну и ту же
точку: рука не двинулась вообще. Это ровно тот отказ, от которого защищает
правило «у топика команд один издатель», и он воспроизводится за минуту.

## Известное поведение, не дефект

- **Снос по остальным осям при джоггинге — лечится ориентацией.** Сначала шлюз
  слал в `/servo_target` единичный кватернион, и подъём схвата на 16 см по `z`
  утаскивал его на 15 см по `x`: у руки пять степеней свободы, решатель не может
  попасть одновременно в произвольную позицию и в произвольную ориентацию и
  размазывает невязку по обеим задачам. После того как в цель стала
  подставляться ТЕКУЩАЯ ориентация из TF, снос упал со 145 мм до 12 мм —
  решателю осталась только позиционная задача. Полностью снос не исчезает, и
  обещать движение «строго вверх» по-прежнему нельзя.
- **`out_of_range` называет ось, которая упёрлась, а не ту, по которой джогали.**
  В нулевой позе рука стоит на x = 0.391, вне коробки, поэтому джог по `z`
  честно жалуется на `x`.
- **Первый оператор раньше начинал с текущей позы, а не из `home`.** Исправлено:
  шлюз уводит руку в `home` сам, как только узнаёт её фактическое положение.

## Что осталось до этапа ROS-бэкенда

Сделано и проверено на живой системе:

- `backends/ros2.py` — подписка на `joint_states` **по именам**, публикация в
  `forward_controller/commands`, положение схвата из TF, джоггинг через
  `/servo_target` с подхватом решения из `/web/ik_cmd`.
- `deploy/Dockerfile.gateway` и полный `compose.dev.yml`.
- Сквозная проверка: команда по WebSocket → `shoulder_pan = +1.1000` в ROS,
  остальные суставы не шелохнулись. `shoulder_pan` первый в порядке команд и
  четвёртый по алфавиту, так что при сопоставлении по индексу поехал бы
  `wrist_flex` — проверка именно на этом и построена.
- Джоггинг: схват поднялся с 0.2265 до 0.4500 (потолок зоны) и вернул
  `out_of_range`.

Осталось:
