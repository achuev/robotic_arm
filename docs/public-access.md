# Публичный доступ: рука из любой точки России

Как открыть стенд посетителю с мобильного интернета, а не только тому, кто
стоит в зале и подключён к тому же вайфаю.

Всё описанное **проверено целиком до аренды сервера**: та же схема поднималась
на этой машине в отдельном сетевом пространстве — тот же WireGuard, тот же
Caddy, тот же путь трафика. Цифры ниже не оценки, а замеры.

---

## Что где живёт

Главное недоразумение, которое стоит снять сразу: **на сервер переносится не
проект, а только точка входа**. Рука подключена к стенду по USB, и ROS, драйвер
и шлюз обязаны остаться рядом с ней.

```
   телефон в сотовой сети
          │  https://arm.example.ru
          ▼
   ┌──────────────────────────────┐
   │  арендованный сервер          │   Caddy: TLS, проксирование
   │  публичный IPv4               │   /api/admin/* наружу не отдаётся
   │  WireGuard 10.8.0.1           │   стенда нет → страница «выключен»
   └──────────────┬───────────────┘
                  │  туннель, поднимает ЕГО стенд
   ┌──────────────▼───────────────┐
   │  стенд в зале, за NAT         │   nginx :8080 → шлюз и сайт
   │  WireGuard 10.8.0.2           │   ROS, драйвер, рука по USB
   └──────────────┬───────────────┘
                  │  только локальная сеть
   ┌──────────────▼───────────────┐
   │  экран рядом с рукой          │   /screen/ — видео во весь экран
   └──────────────────────────────┘
```

Видео — единственное, что не проходит наверх: оно остаётся в зале. Почему
именно так, с замерами, — в разделе «Что идёт через туннель, а что нет».

Связь устанавливает **стенд**: у него нет своего публичного адреса, он стоит за
NAT гостевой сети. Поэтому ничего не надо просить у администратора зала — ни
проброса портов, ни белого IP. Достаточно, чтобы наружу проходил UDP.

Из этого следует главное свойство: **выключить публичный доступ — значит убрать
маршрут**, а не поменять настройку. Пока туннель опущен, сервер физически не
может достучаться до стенда. Ошибиться в конфигурации и случайно оставить руку
открытой миру нельзя.

---

## Что арендовать

**Timeweb Cloud**, Москва или Санкт-Петербург.

| | |
|---|---|
| Образ | Ubuntu 24.04 |
| Ресурсы | 1 vCPU, 1–2 ГБ RAM, 10 ГБ диска |
| Сеть | публичный IPv4 (заказывается отдельно, ~200 ₽/мес) |
| Ориентир по цене | 150–400 ₽/мес за сервер + IP |

Почему именно этот провайдер:

**Российский дата-центр** — главный довод: маршрут до МТС, Мегафона, Билайна,
Tele2 и Yota идёт внутри страны.

**Почасовая оплата.** Сервер поднимается под мероприятие и гасится после.

Про трафик можно не думать. Видео через сервер не идёт (см. ниже), а
управление весит **25 кбит/с на посетителя** — за целый день это меньше
гигабайта. Раньше в этом разделе стояло обратное: пока видео шло через
туннель, безлимит был решающим доводом. Теперь не так.

Подойдёт и любой другой российский VPS с Ubuntu и публичным IPv4 — ничего
специфичного для Timeweb в конфигурации нет.

### Домен

Нужен для HTTPS: сертификат на голый IP не выписывается. Любой регистратор,
200–800 ₽/год. После покупки — **A-запись на IP сервера**, больше ничего.

Без домена тоже заработает, по HTTP на голом IP: браузеры покажут «Не
защищено», но сайт, управление и видео будут работать. Домен добавляется позже
перезапуском одного скрипта.

## Развёртывание: четыре шага

### 1. На стенде — ключи

```bash
sudo deploy/public.sh init
```

Печатает публичный ключ стенда. Приватный остаётся здесь и никуда не уходит.

### 2. На сервере — установка

Скопируйте туда каталог `deploy/relay/` и запустите:

```bash
sudo ./provision.sh \
    --domain arm.example.ru \
    --stand-pubkey <ключ из шага 1> \
    --email you@example.com
```

Ставит WireGuard, Caddy и межсетевой экран, выпускает сертификат. Снаружи
останутся открыты только 22, 80, 443 и 51820/udp.

В конце скрипт печатает **готовую команду для шага 3** — её нужно скопировать.

Перед запуском убедитесь, что A-запись уже разошлась:

```bash
dig +short arm.example.ru      # должен вернуть IP сервера
```

Иначе Let's Encrypt откажет, и сайт будет отдавать ошибку TLS.

### 3. На стенде — адрес сервера

```bash
sudo deploy/public.sh configure \
    --server-pubkey <из шага 2> \
    --endpoint <IP сервера>:51820 \
    --domain arm.example.ru
```

`provision.sh` печатает эту команду целиком — её достаточно скопировать.

Размер пакета в туннеле (`--mtu`) по умолчанию 1280 и подходит любой сети.
Если зал сидит на сотовом модеме, стоит сначала прочитать раздел ниже.

### 4. Включить

```bash
sudo deploy/public.sh on
```

## Каждый день

```bash
sudo deploy/public.sh on       перед мероприятием
sudo deploy/public.sh off      после
sudo deploy/public.sh status   что сейчас происходит
deploy/public.sh qr            табличка с QR на публичный адрес
```

`status` показывает не только «интерфейс поднят» — это ничего не значит,
он поднимется и в пустоту. Проверяется **рукопожатие**: если его не было
больше трёх минут, связи с сервером нет.

`off` рвёт связь с интернетом, но **не трогает руку**. Стенд продолжает
работать в локальной сети по `http://<локальный-ip>:8080`.

Посетитель, оказавшийся в этот момент на середине хода, теряет соединение;
шлюз через 10 секунд отзывает ход, рука останавливается по сторожевому
таймеру. Ничего чинить не нужно.

---

## Что идёт через туннель, а что нет

**Видео наружу не идёт.** Это главное решение всей схемы, и от него зависит
всё остальное.

MJPEG отдаётся КАЖДОМУ смотрящему собственным потоком. Один зритель — 2.9
Мбит/с, и все они уходят через исходящий канал зала. Управление на этом фоне
не весит ничего. Замерено настоящим браузером:

| | вверх (со стенда) | вниз (на стенд) | всего |
|---|---|---|---|
| посетитель смотрит | 17 кбит/с | ≈0 | **17 кбит/с** |
| посетитель управляет | 18 кбит/с | 7 кбит/с | **25 кбит/с** |
| посетитель смотрит видео | +2900 кбит/с | — | **2.9 Мбит/с** |

Разница в **сто с лишним раз**. Поэтому камера в сайте выключена
(`FEATURE_VIDEO=0`), а посетитель видит **3D-модель**: она рисуется по тем же
`joint_states`, что идут в телеметрии, и потому уже оплачена — это те самые
17 кбит/с.

Запрет стоит в двух местах сразу. Флаг в шлюзе убирает камеру из сайта;
ретранслятор отдаёт на `/video/*` и `/screen/*` **404**. Второе важнее
первого: флаг можно включить не подумав, а канал зала от этого шире не
станет.

### Картинку показывает экран у стенда

```
http://<ip стенда>:8080/screen/
```

Отдельная страница: видео во весь экран, чёрный фон, сама переподключается,
раз в десять минут перезапускает поток. Ноутбук или монитор рядом с рукой
открывает её и стоит так весь день.

Поток при этом идёт **по локальной сети** и через модем не проходит вообще.
Значит, качество можно не жалеть — в `deploy/.env` стоит полное разрешение.

### Сколько выдержит

Через туннель на одного посетителя уходит 25 кбит/с. На любом канале, включая
сотовый, первым кончается не он, а **потолок очереди в шлюзе** — 20 человек,
то есть около 0.5 Мбит/с. Дальше упрётесь в тепловой режим руки, а не в сеть.

Сервер при такой нагрузке не делает ничего: 1 vCPU с запасом.

## Если в зале нет интернета: сотовый модем

Рабочий вариант, и схема к нему подходит лучше, чем к гостевому вайфаю.

### Что не является проблемой

**Отсутствие белого IP.** Оператор выдаёт адрес за общим NAT, входящее
соединение до модема невозможно в принципе. Здесь это не важно: связь
устанавливает **стенд**, он дозванивается наружу сам. Схема с прокидыванием
портов не заработала бы; эта работает без единой настройки.

**Смена адреса.** Модем переподключается и получает новый IP. WireGuard это
переживает: стенд шлёт пакеты с нового адреса, сервер узнаёт его по ключу и
обновляет запись. `PersistentKeepalive = 25` не даёт паузе затянуться.

**Полоса.** 25 кбит/с на посетителя. Двадцать человек — полмегабита; столько
отдаёт вверх даже слабая сота. Пока видео не в сайте, полоса не ограничение.

**Объём трафика.** Меньше гигабайта за день. Тариф с пакетом подойдёт.

### Что остаётся проблемой

**Размер пакета.** Самое коварное здесь. Оператор заворачивает трафик в свой
туннель и отъедает часть полутора килобайт. Слишком большой пакет с запретом
фрагментации не режется, а **молча теряется** — и получается худший вид
поломки: `status` показывает рукопожатие, туннель «работает», а сайт не
открывается.

Замерьте канал, по любому адресу в интернете:

```bash
deploy/public.sh mtu 8.8.8.8
```

Значение по умолчанию (1280) выбрано так, чтобы проходить везде, и обычно
менять его не нужно. Если замер посоветует меньше — задайте на **обеих**
сторонах:

```bash
sudo deploy/public.sh configure ... --mtu <значение>   # на стенде
sudo ./provision.sh ... --mtu <значение>               # на сервере
```

**Фильтрация UDP.** Встречается редко. Признак — рукопожатия нет вообще.
Тогда отдайте туннелю 443-й порт: его не режет никто, через него ходит весь
HTTPS.

```bash
sudo ./provision.sh --port 443 ...                       # на сервере
sudo deploy/public.sh configure --endpoint <IP>:443 ...  # на стенде
```

HTTP/3 при этом выключается сам — порт занят туннелем. Сайт работает по
HTTP/2, посетитель разницы не увидит.

### Порядок действий с модемом

1. Воткнуть модем, дождаться интернета на стенде.
2. `deploy/public.sh mtu <любой IP>` — узнать размер пакета.
3. Обычные четыре шага развёртывания, с `--mtu` из пункта 2.
4. `deploy/public.sh status` — убедиться, что рукопожатие есть.
5. Открыть сайт **со своего телефона по сотовой связи**, не по вайфаю зала.

Пятый пункт обязателен: он единственный проверяет весь путь целиком, и делать
это надо до того, как к табличке подойдёт первый посетитель.

## Если видео всё-таки нужно в сайте

Например, показать руку тем, кто в зал не придёт. Тогда честно посчитайте
канал: **каждый** смотрящий стоит отдельного потока.

Включается в `deploy/.env`:

```
FEATURE_VIDEO=1
```

и снимается запрет в `deploy/relay/Caddyfile` — блок `handle /video/*`.
Оба действия нужны: флаг вернёт камеру в сайт, но ретранслятор продолжит
отдавать 404, пока его не поправить.

Замерено, кбит/с на одного зрителя:

| разрешение | fps | q70 | q50 | q40 | q30 |
|---|---|---|---|---|---|
| 640×480 | 15 | **2808** | 2281 | 2037 | 1791 |
| 640×480 | 10 | 1912 | 1519 | 1364 | 1199 |
| 480×360 | 10 | 1530 | 1192 | 1076 | 944 |
| 480×360 | 8 | 1210 | **954** | 857 | 755 |
| 320×240 | 8 | 834 | 658 | **593** | 518 |

Из таблицы видно то, что обычно предполагают неверно: **качество JPEG почти
не помогает.** Сдвиг с 70 до 30 срезает лишь четверть потока, зато заметен на
глаз. Работают разрешение и частота кадров.

На сотовом модеме реальные 2–15 Мбит/с вверх — это от одного до пяти зрителей
в полном качестве и впятеро больше на узком профиле. Профили с готовыми
значениями лежат в `deploy/.env`.

## Что закрыто

**Админка не выходит наружу.** `/api/admin/*` отдаёт 404 — не 403, чтобы
снаружи не было видно даже того, что эти адреса существуют. Аварийная
остановка, снятие оператора и список очереди доступны только из локальной
сети, с самого стенда.

**Ограничитель частоты сообщений** (30/с на соединение) и потолок очереди
(20 человек) работают как и раньше — они в шлюзе, а не в ретрансляторе.

**Публичный доступ выключен по умолчанию.** Туннель не поднимается сам ни
при перезагрузке стенда, ни при старте docker — только вашей командой.

## Симптом → причина

| Симптом | Причина | Что делать |
|---|---|---|
| `status` говорит «рукопожатия ещё не было» | В сети зала закрыт исходящий UDP на 51820, либо неверный `--endpoint` | Проверьте порт: `nc -zvu <IP сервера> 51820`. Гостевые сети иногда режут UDP — тогда нужен другой канал (например, телефон в режиме модема) |
| Сайт отдаёт ошибку TLS | A-запись домена ещё не разошлась либо указывает не туда | `dig +short <домен>` должен вернуть IP сервера. Дальше `systemctl restart caddy` |
| Посетители видят «стенд сейчас выключен», хотя вы его включили | Туннель поднят, но стенд не отвечает на `localhost:8080` | `docker compose -f deploy/compose.prod.yml up -d`. `public.sh on` предупреждает об этом при запуске |
| Рукопожатие есть, но сайт не открывается | Слишком большой MTU: пакеты теряются молча. Классика сотовых сетей | `deploy/public.sh mtu <IP сервера>`, затем `configure --mtu` на стенде и `provision.sh --mtu` на сервере |
| Рукопожатия нет совсем, `--endpoint` верный | Оператор режет UDP на нестандартном порту | Перевести туннель на 443: `provision.sh --port 443`, `configure --endpoint <IP>:443` |
| Экран у стенда показывает «Жду картинку с камеры…» | Камера не отдаёт кадры: не поднялся контейнер либо отвалился USB | `docker compose -f deploy/compose.prod.yml logs camera`. Страница переподключается сама, вмешиваться не нужно |
| Посетитель спрашивает, где видео | Его и нет: в сайте 3D-модель, картинка — на экране у стенда | Так задумано. Если видео нужно и в сайте — раздел «Если видео всё-таки нужно» |
| Модель в сайте не шевелится | Это телеметрия, а не видео: оборвался WebSocket | Смотреть шлюз, а не камеру |
| После перезагрузки стенда доступа нет | Так и задумано: туннель не поднимается сам | `sudo deploy/public.sh on` |
| `provision.sh` ругается на Caddyfile | Версия Caddy старше 2.7 — нет `file_server { status }` | Скрипт ставит Caddy из своего репозитория; проверьте `caddy version` |

## Чего здесь сознательно нет

**Автоматического включения по расписанию.** Публичный доступ открывается
вручную, потому что рядом с рукой должен быть человек. Рука, которую ночью
гоняет в упор неизвестно кто, — не гипотетическая проблема: за публичной
ссылкой оказываются те, кто робота не видит.

**Размножения видеопотока на сервере.** Понадобится, если зрителей станет
больше десятка. Пока не нужно, а сложность заметная.

**Удалённой админки.** Аварийная остановка доступна только со стенда. Это
осознанно: кнопка, останавливающая руку, не должна быть в интернете.
