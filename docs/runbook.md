# Рунбук стенда SO-101

Для того, кто стоит рядом со стендом. Как поднять, как убедиться, что живо, что
делать, когда не работает, и как остановить руку, если что-то пошло не так.

Раздел [«Симптом → причина»](#симптом--причина) — главный. Почти всё, что тут
перечислено, уже ломалось; отлаживать заново не нужно, достаточно узнать симптом.

---

## 1. Из чего состоит стенд

Шесть контейнеров. Наружу торчит **один порт** — nginx.

```
             телефон посетителя
                    │  http://<ip>:8080   (или https://<домен> через туннель)
                    ▼
        ┌────────────────────────┐
        │  web  (nginx)          │   /            → frontend/dist
        │  единственный порт     │   /api, /ws    → шлюз      :8080
        └───────────┬────────────┘   /video/stream→ видео     :8081
                    │
   ╔════════════════▼═══════════════════════════════════════════════╗
   ║  сетевое пространство и /dev/shm контейнера `ros`               ║
   ║                                                                 ║
   ║   ros       ros2_control + joint_state_broadcaster (:8080/:8081 ║
   ║             свободны для соседей)                               ║
   ║   gateway   FastAPI: очередь, сессии, ограничитель скорости     ║
   ║   ik        cartesian_motion_node, cmd_topic:=/web/ik_cmd       ║
   ║   camera    demo_camera.py → /static_camera/image_raw           ║
   ║   video     web_video_server → MJPEG на :8081                   ║
   ╚═════════════════════════════════════════════════════════════════╝
```

Почему так, а не проще:

- **Один origin.** MJPEG показывается обычным `<img src>`. С отдельного порта это
  CORS, а за HTTPS-туннелем ещё и mixed content — картинка просто не появится.
  Плюс в QR помещается ровно один адрес.
- **Общий `/dev/shm`.** FastDDS на одной машине возит данные через разделяемую
  память. Общей сети мало (см. [ловушки](#симптом--причина)).
- **Порты объявлены только у `ros`** — остальные входят в его сетевое пространство
  и своих портов иметь физически не могут.

| Файл | Что это |
|---|---|
| `deploy/compose.dev.yml` | стенд разработки, `hardware_type:=mock`, электроника не нужна |
| `deploy/compose.prod.yml` | боевой стенд: `real`, автоперезапуск, один порт, туннель за профилем |
| `deploy/stand.sh` | обёртка над compose: сама достаёт ADMIN_TOKEN, `restart` = стек целиком |
| `deploy/nginx/so101.conf` | вся маршрутизация одного origin |
| `deploy/video/demo_camera.py` | источник кадров: синтетика / ролик / живая камера |
| `deploy/qr.py` | табличка с QR на печать |
| `deploy/99-so101.rules` | udev: стабильный `/dev/so101_follower` |
| `deploy/so101-stand.service` | автозапуск через systemd |

## 2. Поднять

### Разработка (mock, без электроники)

```bash
cd frontend && npm run build && cd ..        # nginx раздаёт frontend/dist
docker compose -f deploy/compose.dev.yml build
docker compose -f deploy/compose.dev.yml up -d
open http://localhost:8080/
```

Первая сборка образа ROS — долгая (робокин, placo, прогрев кэша описаний).
Дальше подъём стека занимает около минуты: рука ~2 с, IK ~10 с, шлюз ждёт
готовности руки.

Отладочные порты мимо nginx (только dev, только с localhost):
`http://localhost:18080/api/...` — шлюз, `http://localhost:18081/` — видео.

### Боевой стенд

```bash
cd frontend && npm run build && cd ..
export ADMIN_TOKEN=$(openssl rand -hex 24)   # без него стек не поднимется
docker compose -f deploy/compose.prod.yml up -d
```

Перед первым запуском на железе:

```bash
sudo cp deploy/99-so101.rules /etc/udev/rules.d/99-so101.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
ls -l /dev/so101_follower                    # должен быть симлинк на ttyACM*/ttyUSB*
```

Автозапуск при включении питания — `deploy/so101-stand.service`, инструкция
по установке в шапке самого файла.

### Табличка с QR

```bash
python3 -m venv deploy/.venv                            # один раз
deploy/.venv/bin/pip install -r deploy/requirements-qr.txt

# локальный Wi-Fi: адрес машины в сети зала, НЕ localhost
deploy/.venv/bin/python deploy/qr.py http://192.168.1.42:8080 -o tablet.pdf

# публичный туннель
deploy/.venv/bin/python deploy/qr.py https://arm.example.com -o tablet.pdf
```

По умолчанию A5, 300 dpi; `--page a4|a6`, `-o *.png` для экрана. Перед печатью
**проверьте код своим телефоном** — не глазами, а камерой.

### Управление из терминала

```bash
deploy/.venv/bin/python deploy/arm.py state            # положения суставов
deploy/.venv/bin/python deploy/arm.py watch            # живая телеметрия
deploy/.venv/bin/python deploy/arm.py move shoulder_pan 0.3
deploy/.venv/bin/python deploy/arm.py jog  elbow_flex -0.2
deploy/.venv/bin/python deploy/arm.py gripper 0.5
deploy/.venv/bin/python deploy/arm.py preset wave
deploy/.venv/bin/python deploy/arm.py shell            # интерактивно
```

`move` — абсолютная позиция, `jog` — смещение от текущей. Разными командами,
а не флагом: иначе минус читается то как «влево», то как «в позицию −0.2»,
и ошибиться можно молча.

Инструмент ходит **через шлюз**, тем же протоколом, что и сайт
([api.md](api.md)). Из этого следует всё остальное:

* он работает при поднятом стенде и не воюет за последовательный порт;
* он уважает очередь. Если рукой управляет посетитель, терминал встанет в
  очередь и подождёт (`--wait 300`), а не отберёт ход. Отобрать осознанно —
  `--force`, он требует `ADMIN_TOKEN` в окружении;
* ход отдаётся при выходе. Иначе рука осталась бы занятой до таймаута
  бездействия, и следующий человек упёрся бы в «управляет кто-то другой»;
* значения вне предела сустава зажимаются с предупреждением, а не роняют
  команду — так же, как это делает шлюз.

Стенд на другой машине: `--url http://192.168.1.42:8080` либо переменная
`SO101_URL`.

### Напрямую по шине — только при погашенном стенде

```bash
deploy/.venv/bin/python deploy/servo_scan.py           # что на шине
deploy/.venv/bin/python deploy/jog_joint.py --help     # подвинуть один сустав
```

Последовательный порт держит драйвер внутри контейнера, и держит
**монопольно**: пока стек поднят, второй процесс порт не откроет. Поэтому
прямая работа с шиной — это сначала `docker compose -f deploy/compose.prod.yml
down`, и только потом скрипты. Нужна калибровка или смена ID — см.
[hardware-bringup.md](hardware-bringup.md).

### Пропал интернет — запасная панель на стенде

Модем теряет связь: ушла сота, кончился баланс, перегрелся. **Стенд от этого
не ломается.** Сайт раздаёт его собственный nginx, шлюз и ROS живут рядом с
рукой, и всё нужное посетителю есть локально. Интернет добавляет только
публичный доступ — он же первым и отваливается.

```bash
deploy/stand-panel.sh
```

Открывает ту же самую панель на экране стенда, в киоск-режиме. Раскладка на
широком экране своя: ползунки слева, рука справа, ничего не скроллится. Это
**та же страница**, что и на телефоне, а не копия — копия начала бы отставать
от оригинала.

Камера там включена (`?video=1`): поток идёт по локальной сети и ничего не
стоит. Наружу этот параметр бесполезен — ретранслятор отдаёт на `/video/*`
404, запрет стоит не во флаге.

Только видео, для второго монитора:

```bash
deploy/stand-panel.sh --screen
```

Пока панель работает, публичный доступ можно не трогать: как только модем
вернётся, туннель поднимется сам — `PersistentKeepalive` не даст паузе
затянуться. Проверить: `sudo deploy/public.sh status`.

### Публичный доступ — осознанно

Основной способ: свой сервер-ретранслятор и туннель WireGuard, который
поднимает сам стенд. Полностью описан в **[public-access.md](public-access.md)**,
здесь только ежедневные команды.

```bash
sudo deploy/public.sh on       перед мероприятием
sudo deploy/public.sh off      после
sudo deploy/public.sh status   есть ли связь с сервером
deploy/public.sh qr            табличка с QR на публичный адрес
```

`off` убирает маршрут, а не «запрещает» доступ настройкой: сервер после этого
физически не может достучаться до стенда. Руку это не трогает — в локальной
сети стенд продолжает работать.

**Если интернет в зале через сотовый модем** — сначала `deploy/public.sh mtu`,
иначе туннель поднимется, рукопожатие будет, а сайт не откроется. См. раздел
«Если в зале нет интернета» в public-access.md.

**Видео наружу не идёт** и в сайте выключено: посетитель видит 3D-модель,
а картинку показывает отдельный экран рядом с рукой —

```
http://<ip стенда>:8080/screen/
```

Открыть на ноутбуке или мониторе в зале и оставить. Поток идёт по локальной
сети; ретранслятор отдаёт на `/video/*` и `/screen/*` 404. Причина — цена:
посетитель с моделью стоит 25 кбит/с, он же с видео — 2.9 Мбит/с, и поток у
каждого свой.

Альтернатива — Cloudflare Tunnel, если своего сервера нет:

```bash
export TUNNEL_TOKEN=...                      # Cloudflare Zero Trust → Tunnels
docker compose -f deploy/compose.prod.yml --profile tunnel up -d
docker compose -f deploy/compose.prod.yml --profile tunnel stop cloudflared
```

Public hostname туннеля должен указывать на `http://web:80`, а не на шлюз:
иначе мимо nginx пройдут статика и видео.

Публичный доступ выключен по умолчанию не из осторожности вообще, а по
существу: очередь рассчитана на людей, стоящих рядом и видящих руку. За
публичной ссылкой окажутся те, кто руку не видит, — и первым же следствием
будет рука, которую ночью гоняет в упор неизвестно кто.

## 3. Проверить, что живо

Быстрый круг, всё через один порт — как его увидит посетитель:

```bash
docker compose -f deploy/compose.dev.yml ps          # все running, ros/gateway/video healthy

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/          # 200, сайт
curl -s http://localhost:8080/api/health                                 # {"ok":true}
curl -s http://localhost:8080/api/status                                 # robot/queue
curl -s http://localhost:8080/api/config | grep -o '"video_url":"[^"]*"'  # /video/stream

# видео: заголовок должен быть multipart, тело — идти непрерывно
curl -sI 'http://localhost:8080/video/stream' | head -3
curl -s --max-time 3 http://localhost:8080/video/stream | grep -ac boundarydonotcross
```

Последняя команда печатает число кадров за три секунды. Норма — **35–46**
(поток 15 fps; сразу после перезапуска `camera` первые секунды дают меньше).
`0` — кадров нет, идите в [симптомы](#видео).

Отдельно стоит знать, **как выглядит стенд со сломанной рукой**: сайт всё равно
открывается (`/` → 200), а 502 приходит только на `/api`, `/ws` и `/video`.
Так задумано — у nginx нет `depends_on`. Посетитель, отсканировавший QR, должен
увидеть страницу с честным «робот недоступен», а не «соединение отклонено»:
по второму он решит, что сломан его телефон.

Изнутри ROS (когда нужно копнуть глубже):

```bash
docker exec so101-ros /entrypoint.sh bash -lc '
  ros2 node list
  ros2 topic hz /follower/joint_states
  ros2 control list_controllers -c /follower/controller_manager
'
```

`ros2 control list_controllers` **без** `-c /follower/controller_manager` не найдёт
менеджер и будет молча ждать таймаута — менеджер живёт в пространстве имён.

## 4. Аварийная остановка

Четыре уровня, от мягкого к жёсткому. Начинайте сверху: чем ниже, тем дольше
возвращать стенд в работу.

### Уровень 1. Остановить руку, оставив стенд живым

```bash
curl -X POST -H "X-Admin-Token: $ADMIN_TOKEN" http://localhost:8080/api/admin/estop
```

Ход у текущего оператора отзывается немедленно, очередь замораживается (люди
остаются на местах), публикация команд прекращается. Сайт показывает баннер
«Робот остановлен оператором». Рука остаётся там, где стояла, и **держит момент**.

Снять:

```bash
curl -X POST -H "X-Admin-Token: $ADMIN_TOKEN" http://localhost:8080/api/admin/release_estop
```

Проверить, что подействовало: `curl -s http://localhost:8080/api/status` → `"robot":"estop"`.

### Уровень 2. Снять только текущего оператора

Когда конкретный человек делает что-то неудачное, а стенд в целом в порядке:

```bash
curl -X POST -H "X-Admin-Token: $ADMIN_TOKEN" http://localhost:8080/api/admin/kick
curl -s -H "X-Admin-Token: $ADMIN_TOKEN" http://localhost:8080/api/admin/queue   # кто там вообще
```

Ход уходит следующему в очереди, рука уезжает в `home`.

### Уровень 3. Погасить шлюз

```bash
docker compose -f deploy/compose.prod.yml stop gateway
```

Единственный издатель команд исчезает; рука замирает в текущей позиции и держит
момент. Сайт при этом отдаёт 502 — посетители видят, что стенд выключен, а не
делают вид, что управляют.

### Уровень 4. Обесточить сервоприводы

Физический выключатель на блоке питания руки.

Перед тем как дёргать питание, уберите из-под руки всё, что она может уронить
или чем ударить. Это уровень «человек в опасности», а не «что-то странно себя
ведёт».

Замерено на этой руке: при снятии момента она **не складывается** — редуктор
1/345 держит её в той позе, где застали, до тика. Но проверять это на весу,
когда под рукой что-то стоит, не стоит: одно дело поза парковки, другое —
рука, вытянутая горизонтально с грузом в схвате.

### Чего не делать

- `docker compose down` как способ остановить руку. Он делает это КОРРЕКТНО
  (мягкая посадка, потом снятие момента — см. §5.5), но это уровень 3 плюс потеря
  видео, сайта и очереди — дольше и грязнее, чем `estop`.
- Возвращать питание, не проверив глазами, где стоит рука: после включения она
  подхватит последнюю цель и поедет к ней.

## 5. Симптом → причина

### Сеть и контейнеры

| Симптом | Причина | Что делать |
|---|---|---|
| Все контейнеры `running`, но `/api/health` снаружи отдаёт **502**, а изнутри шлюз отвечает 503 | Перезапустили **только** `ros`. Соседи по сетевому пространству остались в уже уничтоженном namespace: снаружи в контейнере `ros` никто не слушает 8080, шлюз при этом жив и в порядке. Docker сам это не чинит и статус `running` не меняет | Перезапустить соседей: `docker compose -f deploy/compose.prod.yml restart gateway ik camera video`. Правило: перезапускать **стек целиком**, а не один сервис |
| `ros2 node list` не показывает чужие ноды; на топике `Subscription count: 3`, а данные не идут вообще; `/api/health` честно отдаёт 503 | Контейнеры делят сеть, но **не делят `/dev/shm`**. FastDDS на одной машине возит данные через разделяемую память, и без общего IPC он молчит, не жалуясь | В compose донор — `ipc: shareable`, остальные — `ipc: "service:ros"`. Не убирать. Донор без `shareable` не даст присоединиться: `can't join IPC of container ... non-shareable IPC` |
| `network_mode: host` не работает | Docker Desktop под macOS: «хост» там — скрытая виртуальная машина LinuxKit | Проброс портов, как в обоих compose-файлах. На Linux-стенде host тоже не нужен |
| nginx отдаёт 502 на всё, в логе `ros could not be resolved` | Контейнер `ros` не поднялся, либо кто-то руками делал `docker network connect` и потерял alias сервиса | `docker compose ... up -d --force-recreate`. Руками сети не трогать: alias `ros` ставит compose, ручной `connect` регистрирует только имя контейнера |

### Видео

| Симптом | Причина | Что делать |
|---|---|---|
| На сайте «Камера не отвечает», `/video/stream` даёт 502 | Не поднялся сервис `video` или `camera` | `docker compose ... ps`, дальше `docker logs so101-camera` |
| `/video/stream` отвечает 200, но кадров ноль, картинка не появляется | Никто не публикует в `/static_camera/image_raw`, либо **не сходится QoS**: если издатель кадров BEST_EFFORT, а `web_video_server` подписан RELIABLE, поток молча пуст | Проверить: `docker exec so101-ros /entrypoint.sh ros2 topic info /static_camera/image_raw -v` → у издателя должно быть `RELIABLE` |
| Кадры идут, но появляются рывками или с огромной задержкой | В nginx для потока не выключена буферизация | В `deploy/nginx/so101.conf` у `/video/stream` обязателен `proxy_buffering off` |
| `web_video_server` не стартует, «address already in use» | Он по умолчанию слушает **8080** — тот же порт, что и шлюз, а сетевое пространство у них общее | `-p port:=8081`, как в compose |
| Видео есть, но это застывший кадр | Источник умер, а последний кадр остался в буфере | На синтетическом потоке видно сразу: должна ехать вертикальная полоса развёртки и тикать счётчик кадров. Нет движения — `docker restart so101-camera` |
| Хочется переключиться на настоящую камеру | — | В `compose.prod.yml` у сервиса `camera`: `source:=/dev/so101_camera` + `devices:`. Пакеты `gscam`/`v4l2_camera` в образе **не стоят** (`ROSDEP_SKIP_KEYS` в `deploy/Dockerfile.ros`), поэтому камера читается через OpenCV нашим узлом. Камерный стек апстрима — альтернатива, но требует пересборки образа |

### Рука

| Симптом | Причина | Что делать |
|---|---|---|
| **Двигается не тот сустав**: просили локоть — поехало плечо | Порядок суставов в команде и в обратной связи **разный**. Команда: `shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper`. `joint_states`: по алфавиту — `elbow_flex, gripper, shoulder_lift, shoulder_pan, wrist_flex, wrist_roll` | Читать `joint_states` строго **по имени**, никогда по индексу. Совпадут только нули — то есть в тестах не проявится, а на стенде поедет не то |
| Рука не двигается **вообще**, команды принимаются, ошибок нет | У топика команд **два издателя**. Второй (диагностический скрипт, ручной `ros2 topic pub`) перебивает шлюз, и рука стоит | Убрать второго. `ros2 topic info /follower/forward_controller/commands` → `Publisher count` должен быть ровно 1 |
| Схват при джоггинге по `z` едет **вниз** вместо вверх | Положение схвата считается собственной моделью, а не берётся из TF. Две геометрии в одном контуре обратной связи уводят руку | Точка берётся только из TF: `base_link` → `gripper_frame_link`, **без префикса**. `follower/base_link` не существует |
| Джог по `z` возвращает `out_of_range` с осью `x` | Так и задумано: сообщается ось, которая **упёрлась**, а не та, по которой джогали. В нулевой позе рука стоит на `x = 0.391`, вне рабочей коробки | Увести руку в `home` (0.293, 0.000, 0.206) и джогать оттуда |
| На свежем стенде первый посетитель сразу получает `out_of_range` | Первый оператор начинает с текущей позы, а не из `home`; на пустом стенде передавать ход не от кого. Нулевая поза — вне рабочей зоны намеренно (там якобиан вырожден) | Увести руку в `home` при старте стенда — служебным слоем, через ограничитель скорости, а не `backend.go_home()`, иначе рука дёрнется на полной скорости |
| Джог «строго вверх» уводит схват и по другим осям на сантиметр-полтора | Известное поведение, не дефект: у руки пять степеней свободы, невязка размазывается между позицией и ориентацией. С подстановкой текущей ориентации из TF снос упал со 145 мм до 12 мм, но не исчез | Обещать движение строго по одной оси нельзя |
| Рука замерла посреди движения, команды больше не действуют | Сработал watchdog (3 с без единого сообщения от клиента). Он **сбрасывает цель в текущую позицию**, и вернувшийся `ping` движение не возобновляет | Нужна новая команда от человека. Так задумано: `ping` шлётся автоматически и доказывает лишь, что вкладка жива |
| `ros2 control list_controllers` висит и ничего не выводит | Менеджер контроллеров в пространстве имён | `-c /follower/controller_manager` |
| `ros2 topic hz` пишет «does not appear to be published yet», а потом печатает частоту | Ложная тревога самого `hz`. На больших сообщениях (кадры 640×480) он ещё и занижает частоту | Мерить кадры по MJPEG-потоку, как в разделе 3 |

### Железо (появится вместе с электроникой)

| Симптом | Причина | Что делать |
|---|---|---|
| Рука не поднимается: `/dev/so101_follower` нет | Не установлены udev-правила, или переходник другой модели | `ls -l /dev/ttyACM* /dev/ttyUSB*`, затем `udevadm info --query=property --name=/dev/ttyACM0 \| egrep 'ID_VENDOR_ID\|ID_MODEL_ID'` и сверить с `deploy/99-so101.rules` |
| Симлинк снаружи есть, а в контейнере рука «есть в /dev, но не отвечает» | Кабель передёргивали **после** старта контейнера. `devices:` пробрасывает устройство по номеру major:minor, который выясняется один раз при старте; после переподключения ядро выдаёт новый номер, и внутри остаётся мёртвый узел | Перезапустить стек целиком |
| Симлинк указывает на узел, из которого не идут кадры | UVC-камера регистрирует два `/dev/video*`, второй отдаёт метаданные | В правиле обязателен `ATTR{index}=="0"` |
| Драйвер валит инициализацию: `configure_joints_ -> check_head -> read_exact [Read timeout]`, при этом порт открылся и сервоприводы отвечают на `deploy/servo_scan.py` | Таймаут чтения у драйвера — 5 мс, а параметры приводов пишутся в EEPROM, и после серии записей привод отвечает не сразу. Падало стабильно на последнем параметре схвата (`protection_current`), то есть после ~35 записей подряд | Уже вылечено: `deploy/Dockerfile.ros` патчит таймаут на 50 мс при сборке. Если симптом вернулся — проверьте, что патч применился: сборка печатает `timeout_ = std::chrono::milliseconds(50)` |
| **Схват сам сжимается и упирается** сразу после старта стека, остальные суставы стоят | Схват оказался ВНЕ пределов, записанных ему в EEPROM. Драйвер задаёт целью текущее положение, привод не принимает цель вне своих пределов и выдавливает сустав к ближайшему допустимому | Признак того, что при калибровке сустав не прогнали до упора. `deploy/servo_calibrate.py save` теперь это ловит и отказывается писать. Перекалибровать: `center --joints gripper` → `record --joints gripper` → `save` |
| Схват раскрывается не полностью, команда «раскрыть» упирается в железо | Ноль схвата поставлен посередине хода, а URDF ждёт ноль на ЗАКРЫТОМ положении: его предел −0.17…1.75 рад почти весь в плюс | При калибровке середины схват должен быть **сжат**, а не приоткрыт. Проверка: `homing_offset` схвата должен получиться около 1500 (у эталонной руки апстрима 1573, у нашей 1479) |
| Контейнер `ros` уходит в **бесконечный перезапуск**, в логе `LibSerial::NotOpen` и `terminate called` | Драйвер Feetech на недоступном порту не деградирует, а **бросает исключение и роняет весь `ros2_control_node`**. Проверено: `Open [/dev/so101_follower]: Bad file descriptor` → `terminate`. С `restart: unless-stopped` это crash-loop, а не «рука не поднялась» | Сначала убедиться, что симлинк есть и порт открывается (`ls -l /dev/so101_follower`, пользователь в `dialout`). Стек поднимать только после этого — до появления железа `hardware_type:=real` запускать бессмысленно |
| Рука сама шевелится в пустом зале | Режим привлечения внимания: нет ни оператора, ни очереди дольше 120 с. Это штатно, см. §5.5 | Выключается `ATTRACT_ENABLED=0` |
| При остановке рука дёрнулась на треть секунды и встала; в логе `publisher's context is invalid` | rclpy по умолчанию сам ловит SIGTERM и гасит свой контекст РАНЬШЕ, чем шлюз доходит до мягкой посадки | Уже вылечено: бэкенд поднимает rclpy с `SignalHandlerOptions.NO`, сигналы обрабатывает uvicorn. Если симптом вернулся — проверьте этот параметр в `backends/ros2.py` |
| В логе шлюза `используются захардкоженные пределы суставов (fallback)` | В контейнер не проброшен URDF, и клэмп работает по значениям из апстрима, а не по вашей сборке | `URDF_PATH` и монтирование `so101_follower.generated.urdf` в `compose.prod.yml` |
| Рука поднялась, но нули суставов не там, и она бьётся в упоры | В `so101_bringup/config/hardware/follower_joints.yaml` лежит калибровка **чужой руки** (`homing_offset`, `range_min/max` автора апстрима). Апстрим предупреждает об этом прямым текстом в `upstream/docs/hardware.md` | Пройти setup + calibration через LeRobot на **своей** руке; значения пишутся в EEPROM сервоприводов и оттуда и берутся. Чужой YAML не подставлять |
| Стек поднимается ПОЛНОСТЬЮ, рука живёт 12–15 с, затем `FeetechHardwareInterface::read -> sync_read -> check_head -> read_exact [Read timeout]` и `Deactivating ... [ SO101_follower_SYSTEM ]`. Повторяется с точностью до секунды | Один привод неисправен. Под напряжением он жрёт ток, через фиксированное время срабатывает его защита по перегрузке, привод замолкает — и `sync_read` роняет **весь** железный компонент со всеми контроллерами. Один больной сустав гасит всю руку, и по логу не видно, какой именно | Найти его по температуре (рецепт ниже) и заменить. НЕ ослаблять `overload_torque`, чтобы «привод не замолкал»: это снятие единственного предохранителя с привода, который уже греется |

### Как найти больной привод по температуре

В логе `ros` виден только результат — молчание шины. Какой из шести приводов
замолчал, он не сообщает. Зато `servo_scan.py` читает температуру каждого, и
больной выдаёт себя разницей на порядок.

```bash
deploy/stand.sh down
deploy/.venv/bin/python deploy/servo_scan.py     # ЗАМЕР ДО

deploy/stand.sh up                               # дождаться отказа, 12–15 с
deploy/stand.sh stop ros                         # снять момент, освободить порт
deploy/.venv/bin/python deploy/servo_scan.py     # ЗАМЕР ПОСЛЕ
```

Виновник — тот, у кого прирост на порядок больше соседей. На реальном случае
(13.09.2026, `shoulder_pan`) это выглядело так: **+8…13 °C против +1…2 °C** у
остальных пяти, дважды воспроизведено.

Чего этот рецепт стоит: он не зависит от догадок о причине. Проверено, что
симптом НЕ объясняется ни выходом сустава за пределы EEPROM (отказ повторился,
когда все шесть стояли внутри диапазона с запасом 450+ тиков), ни просадкой
питания (12.5–12.7 В ровно во всех замерах), ни шиной (все шесть приводов
отвечают на `servo_scan.py` до и после).

Отдельный признак, отделяющий сдохший привод от механического заклинивания:
поставьте ему `max_torque_limit: 0` в `deploy/so101_follower_joints.yaml`.
Заклинивший перестанет греться, потому что перестанет толкать. Неисправный
греется всё равно — привод, который выделяет тепло с ЗАДАННЫМ нулевым моментом,
неисправен электрически, и лечится только заменой.

**Возвращая `max_torque_limit`, ставьте значение, а не удаляйте строку.**
Драйвер пишет это поле в EEPROM, только если оно есть в yaml; после удаления
строки в приводе останется ноль, и сустав будет мёртвым молча. Заводское
значение — 1000 (у схвата намеренно 500).

## 5.5. Что стенд делает сам

Два движения происходят БЕЗ человека за пультом. Знать о них надо: иначе
шевелящаяся рука в пустом зале выглядит как отказ.

### Привлечение внимания

Если нет ни оператора, ни очереди дольше `ATTRACT_AFTER_SEC` (120 с) — рука
играет случайный жест и возвращается в `home`. Не чаще, чем раз в
`ATTRACT_PERIOD_SEC` (240 с). Стоящий манипулятор читается как выключенный,
мимо него проходят.

Не срабатывает: пока ход у человека, пока в очереди кто-то ждёт, при
аварийной остановке. Появившийся посетитель обнуляет отсчёт простоя.

Выключить на ходу: `ATTRACT_ENABLED=0 docker compose ... up -d gateway`.

### Мягкая посадка

Перед остановкой шлюз уводит руку в низкую позу (схват в 5 см над столом) и
только потом гасится. Без этого рука остаётся там, где её застали, и при
снятии момента падает с этой высоты.

В логе это выглядит так:

```
мягкая посадка: увожу руку в позу парковки
мягкая посадка: рука на месте
```

Занимает меньше секунды. Если вместо второй строки пришло «не успели за N с»
— рука осталась где-то по дороге; уберите из-под неё всё, прежде чем снимать
питание.

**Работает только если контейнер `ros` ещё жив.** `docker compose stop
gateway` и `down` порядок соблюдают (gateway зависит от ros и гасится
раньше), а `docker stop so101-ros` — нет.

### Снятие момента

Сразу после посадки `ros` гасится, и драйвер снимает момент со всех шести
приводов — рука становится свободной. Проверить: `deploy/servo_scan.py`
должен показать позу парковки, а приводы не должны сопротивляться руке.

Это работает благодаря `stop_signal: SIGINT` у сервиса `ros` в compose.
По умолчанию Docker шлёт SIGTERM, и `ros2 launch` завершается жёстко:
`controller_manager` не успевает деактивировать оборудование, `on_deactivate`
драйвера не вызывается, и **приводы остаются под напряжением**, держа последнюю
позу до выдёргивания питания. Внешне неотличимо: рука так же стоит в парковке,
только «каменная». Если симптом вернулся — проверьте этот параметр.

## 6. Обновление стенда

```bash
git pull
cd frontend && npm run build && cd ..                       # dist раздаётся напрямую
docker compose -f deploy/compose.prod.yml build              # если менялись образы
docker compose -f deploy/compose.prod.yml up -d --force-recreate
```

Фронтенд подхватывается без пересборки образов: `frontend/dist` смонтирован в
nginx. Обновление статики видно посетителю сразу — `index.html` отдаётся с
`Cache-Control: no-cache`, а файлы в `assets/` содержат хэш в имени и кэшируются
навсегда.

Если менялся только `deploy/nginx/so101.conf`:

```bash
docker compose -f deploy/compose.prod.yml exec web nginx -t     # проверить синтаксис
docker compose -f deploy/compose.prod.yml exec web nginx -s reload
```

## 7. Что проверить на живом железе

### 7.0 Что обязано быть сделано ДО первого `hardware_type:=real`

Не проверки, а предусловия. Без них стенд не поднимется или поднимется опасно.

1. **Прошить сервоприводы: ID 1…6 и baudrate.** Делается по одному, до сборки
   руки, штатным инструментом LeRobot (`lerobot` — отдельный пакет, в образе
   стенда его нет и не должно быть). Значения пишутся в EEPROM.
2. **Откалибровать руку через LeRobot.** `homing_offset`, `range_min/max`
   ложатся в EEPROM сервоприводов и оттуда берутся драйвером. Готовые
   `so101_bringup/config/hardware/follower_joints.yaml` и `lerobot_*.json` —
   **чужая рука**, апстрим предупреждает об этом прямым текстом
   (`upstream/docs/hardware.md`). Подставлять их нельзя.
3. **udev + группа `dialout`.** Правила из `deploy/99-so101.rules`, затем
   `sudo usermod -aG dialout,video $USER` и перелогиниться.
4. **Убедиться, что порт открывается**, прежде чем поднимать стек: драйвер на
   недоступном порту роняет `ros2_control_node` целиком, а `restart:
   unless-stopped` превращает это в crash-loop (см. таблицу «Железо»).

Плагин `feetech_ros2_driver/FeetechHardwareInterface` в образе **есть** —
собирается в `deploy/Dockerfile.ros`. Проверено: с `hardware_type:=real` он
грузится и доходит до открытия `/dev/so101_follower`; дальше нужна железка.

### 7.1 Проверки после подключения

Здесь, на mock-стенде, проверить нельзя — список для дня, когда приедет электроника.

1. `ls -l /dev/so101_follower` после установки правил и **после** передёргивания
   кабеля: симлинк должен появиться сам.
2. Направление и величина хода каждого сустава: подать по одному суставу
   небольшую цель и глазами сверить с подписью на слайдере.
3. Пределы из URDF против физических упоров — не бьётся ли рука в конструкцию
   раньше, чем упрётся в программный предел.
4. `home` при передаче хода: рука должна доезжать, а не дёргаться.
5. Аварийная остановка уровня 4 — заранее, на пустом столе: посмотреть, как
   именно складывается обесточенная рука.
6. Камера: `source:=/dev/so101_camera`, кадры в `/video/stream`, задержка
   картинки относительно движения руки (на 15 fps ожидаемо 0.2–0.4 с).
7. Тепловой режим сервоприводов после часа работы очереди.
